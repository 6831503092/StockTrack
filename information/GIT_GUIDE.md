## 1. ภาพรวมและสถาปัตยกรรม 4 ด่านของ Git (Git Mental Model)

เพื่อให้เห็นภาพง่ายที่สุด ให้จินตนาการว่า **Git คือ "ระบบเซฟเกม (Checkpoint)" ผสมกับ "การส่งกล่องพัสดุ"** 

ไฟล์ในเครื่องของเราจะเดินทางผ่าน **4 พื้นที่** เสมอ:

```text
[ 1. Working Directory ]  ──(git add)──►  [ 2. Staging Area ]  ──(git commit)──►  [ 3. Local Repo ]  ──(git push)──►  [ 4. GitHub ]
  (โต๊ะทำงานที่เราแก้โค้ด)                  (กล่องพัสดุเตรียมส่ง)                    (จุดเซฟในเครื่องเรา)               (คลาวด์ส่วนกลาง)
```

1. **Working Directory (โต๊ะทำงาน):**
   - คือไฟล์จริงๆ ในโฟลเดอร์ที่เราเปิดพิมพ์โค้ดอยู่ใน VS Code
2. **Staging Area (กล่องพัสดุ):**
   - เมื่อแก้ไฟล์เสร็จ เราใช้คำสั่ง `git add` เพื่อ **"หยิบไฟล์ใส่กล่องเตรียมเซฟ"**
3. **Local Repository (จุดเซฟในเครื่องเรา):**
   - เราใช้คำสั่ง `git commit` เพื่อ **"ปิดฝากล่องพร้อมแปะป้ายชื่อ"** จุดนี้โค้ดจะถูกบันทึกลงฐานข้อมูล Git ในเครื่องเราอย่างถาวร (ออฟไลน์ก็ทำได้)
4. **Remote Repository (GitHub):**
   - เราใช้คำสั่ง `git push` เพื่อ **"ยกกล่องขึ้นรถส่งไปเก็บบน GitHub"** เพื่อให้เพื่อนร่วมทีมดาวน์โหลดไปใช้ต่อได้

## 2. 5 คำสั่งหลักที่ใช้ 90% ในชีวิตประจำวัน (The Daily 5 Commands)

### 2.1 `git status` — ส่องดูสภาพปัจจุบัน (คำสั่งที่ควรกดบ่อยที่สุด)
ใช้ตรวจสอบว่าตอนนี้เราอยู่ที่ Branch ไหน มีไฟล์อะไรถูกแก้บ้าง และมีไฟล์ไหนถูกใส่กล่องแล้วหรือยัง
```bash
git status
```
* 🔴 **สีแดง (Untracked / Modified):** ไฟล์มีการเปลี่ยนแปลง แต่อยู่นอกกล่อง (ยังไม่ได้สั่ง `add`)
* 🟢 **สีเขียว (Changes to be committed):** ไฟล์ถูกหยิบใส่กล่องแล้ว พร้อมบันทึกจุดเซฟ

---

### 2.2 `git add` — หยิบไฟล์ใส่กล่อง (Stage)
* **หยิบทุกไฟล์** ที่มีการเปลี่ยนแปลงใส่กล่องพร้อมกัน:
  ```bash
  git add .
  ```
* **หยิบเฉพาะบางไฟล์** (แนะนำเมื่อต้องการแยกเซฟทีละส่วน):
  ```bash
  git add src/main/resources/static/index.html
  ```

---

### 2.3 `git commit` — กดบันทึกจุดเซฟ (Save Checkpoint)
เป็นการบันทึกประวัติการเปลี่ยนแปลงลงเครื่องตัวเอง โดยต้องใส่ข้อความระบุว่าเราทำอะไรไปเสมอ:
```bash
git commit -m "feat(staff): ออกแบบตารางตรวจรับสินค้าหน้า Receiving"
```
> [!TIP]
> **รูปแบบข้อความ Commit ที่ดี (Conventional Commits):**
> - `feat: ...` เมื่อเพิ่มฟีเจอร์หรือหน้าเว็บใหม่
> - `fix: ...` เมื่อแก้บั๊กหรือแก้โค้ดที่ผิดพลาด
> - `style: ...` เมื่อปรับแต่ง CSS, สี, ความสวยงาม
> - `docs: ...` เมื่อแก้ไขเอกสารหรือ README

---

### 2.4 `git push` — ส่งขึ้น GitHub
ส่งจุดเซฟที่เรา Commit ไว้ในเครื่อง ขึ้นไปเก็บบน GitHub:
```bash
git push
```
*(กรณีที่เป็น Branch ใหม่ที่เพิ่งสร้างในเครื่องครั้งแรก Git จะให้สั่งผูกกับ GitHub ด้วย `-u origin <ชื่อbranch>`)*
```bash
git push -u origin feature/frontend-staff
```

---

### 2.5 `git pull` — ดึงงานล่าสุดจาก GitHub ลงเครื่อง
เมื่อเพื่อนอัปเดตโค้ดขึ้น GitHub เราต้องดึงโค้ดล่าสุดลงมารวมกับเครื่องตัวเอง:
```bash
git pull origin main
```

---

## 3. ระบบกิ่งและการรวมงาน (Branching & Merging)

### ทำไมต้องแตกกิ่ง (Branch)?
Branch เปรียบเสมือน **"โลกคู่ขนาน"** ทำให้ทุกคนสามารถแยกย้ายกันไปแก้โค้ดพร้อมกันได้โดยไม่แย่งไฟล์กันและไม่ทำให้กิ่งหลักพัง:

```text
main:                   ──●───────────────────────●───────────────────────● (กิ่งหลักของทีม)
                           \                     / (Pull Request)
feature/frontend-staff:     └──●───────●───────●/                           (กิ่งของ Staff)
```

### คำสั่งจัดการ Branch ที่จำเป็น:
1. **ดูว่ามี Branch อะไรบ้างในเครื่อง (และเช็คว่าเราอยู่กิ่งไหน):**
   ```bash
   git branch
   ```
   *(กิ่งที่มีเครื่องหมาย `*` สีเขียวนำหน้า คือกิ่งที่เรากำลังยืนอยู่)*

2. **สร้างกิ่งใหม่ และสลับไปที่กิ่งนั้นทันที (ตั้งชื่อขึ้นต้นด้วย `feature/` เสมอ):**
   ```bash
   git checkout -b feature/frontend-staff
   ```

3. **สลับไปกิ่งเดิมที่มีอยู่แล้ว:**
   ```bash
   git checkout main
   ```

4. **ลบกิ่งที่ไม่ใช้แล้ว (หลังจากรวมงานเสร็จ):**
   ```bash
   git branch -d feature/frontend-staff
   ```

## 4. ลำดับการทำงานจริงในแต่ละวันของโปรเจกต์นี้ (Daily Team Workflow)

เพื่อให้งานไม่ชนกัน ทุกคนในทีมต้องปฏิบัติตาม **วงรอบการทำงาน (Daily Loop)** ดังนี้:

### สเต็ปที่ 1: ก่อนเริ่มเขียนโค้ดทุกครั้ง (ดึงของใหม่)
1. สลับไปที่กิ่งหลักของทีม `main` แล้วดึงโค้ดล่าสุด:
   ```bash
   git checkout main
   git pull origin main
   ```
2. สลับกลับมาที่กิ่งของตัวเอง (เช่น `feature/frontend-staff`) แล้วดึงอัปเดตจาก `main` มารวม:
   ```bash
   git checkout feature/frontend-staff
   git merge main
   ```

### สเต็ปที่ 2: นั่งเขียนโค้ดและทดสอบ
- เขียนโค้ดเฉพาะในโฟลเดอร์ของตัวเอง (เช่น `static/staff/` และ `css/staff.css`)
- ทดสอบรัน `.\mvnw.cmd spring-boot:run` บนเครื่องตัวเอง

### สเต็ปที่ 3: เซฟงานและส่งขึ้น GitHub
```bash
git status                                      # เช็คความเรียบร้อย
git add .                                       # ใส่กล่อง
git commit -m "feat(staff): เสร็จงานส่วนตรวจรับ"       # เซฟจุด Checkpoint
git push -u origin feature/frontend-staff       # ส่งขึ้น GitHub
```

### สเต็ปที่ 4: รวมโค้ดเข้ากิ่งกลาง (Pull Request บนเว็บ GitHub)
1. เปิดหน้าเว็บ GitHub ของโปรเจกต์: [https://github.com/6831503092/StockTrack](https://github.com/6831503092/StockTrack)
2. คลิกปุ่มสีเขียว **"Compare & pull request"**
3. ตรวจสอบให้ปลายทางเป็น **`base: main`** $\leftarrow$ **`compare: feature/frontend-staff`**
4. กด **"Create pull request"** และกด **"Merge pull request"** โค้ดของเราจะเข้าไปรวมกับ `main` โดยสมบูรณ์

## 5. คู่มือรับมือและแก้ปัญหายอดฮิต (Troubleshooting & Emergency)

### 🚨 ปัญหาที่ 1: "เขียนโค้ดเละเทะ อยากย้อนไฟล์กลับสภาพเดิมตอนเซฟล่าสุด"
ถ้ายังไม่ได้สั่ง `git add` และต้องการทิ้งการแก้ไขทั้งหมด:
* ย้อนกลับเฉพาะไฟล์นั้น:
  ```bash
  git restore src/main/resources/static/staff/dashboard.html
  ```
* ย้อนกลับทุกไฟล์ในโปรเจกต์:
  ```bash
  git restore .
  ```

---

### 🚨 ปัญหาที่ 2: "เผลอ `git add` ไปแล้ว แต่อยากเอาออกจากกล่อง"
```bash
git restore --staged <ชื่อไฟล์>
# หรือยกเลิกทุกไฟล์ที่ add ค้างไว้:
git restore --staged .
```

---

### 🚨 ปัญหาที่ 3: "เพิ่ง Commit ไป แต่ลืมเขียนบางอย่าง หรือพิมพ์ข้อความผิด"
แก้โค้ดที่ตกหล่น สั่ง `git add .` แล้วรวมเข้าไปใน Commit ล่าสุดได้ทันทีโดยไม่ต้องสร้าง Commit ใหม่:
```bash
git commit --amend -m "ข้อความใหม่ที่ถูกต้อง"
```

---

### 🚨 ปัญหาที่ 4: "เกิด Merge Conflict (โค้ดชนกัน) แก้อย่างไร?"
**Merge Conflict** เกิดขึ้นเมื่อคุณและเพื่อน **แก้ไขไฟล์เดียวกันที่บรรทัดเดียวกัน** แล้วนำมารวมกัน Git จะไม่ตัดสินใจแทนเรา แต่จะแทรกเครื่องหมายเตือนลงในไฟล์แบบนี้:

```html
<<<<<<< HEAD (โค้ดที่เราเขียนในกิ่งปัจจุบัน)
<button class="btn-primary">ยืนยันการรับสินค้า</button>
=======
<button class="btn-success">ตรวจรับสำเร็จ</button>
>>>>>>> develop (โค้ดของเพื่อนที่ดึงมาจากกิ่งอื่น)
```

**วิธีแก้ไข:**
1. เปิดไฟล์นั้นใน VS Code จะมีปุ่มลอยขึ้นมาเหนือโค้ดให้กดเลือกง่ายๆ:
   - **Accept Current Change:** เลือกเก็บโค้ดของเรา
   - **Accept Incoming Change:** เลือกใช้โค้ดของเพื่อน
   - **Accept Both Changes:** เก็บไว้ทั้งสองอัน
   - หรือลบเส้น `<<<<<<<`, `=======`, `>>>>>>>` ทิ้งด้วยมือแล้วเรียบเรียงโค้ดใหม่
2. เมื่อจัดการข้อความขัดแย้งหมดแล้ว ให้สั่ง:
   ```bash
   git add .
   git commit -m "fix: resolve merge conflict"
   ```

---

### 🚨 ปัญหาที่ 5: "ดูประวัติย้อนหลังว่าใครทำอะไรไปบ้าง"
พิมพ์คำสั่งนี้เพื่อดูประวัติ Commit เป็นบรรทัดสั้นๆ พร้อมแผนภาพกิ่งสวยงาม:
```bash
git log --oneline --graph --decorate -n 10
```

## 6. ตารางสรุปคำสั่งย่อพกพา (Git Cheat Sheet)

| คำสั่ง | ความหมาย / การใช้งาน |
| :--- | :--- |
| `git status` | ตรวจสอบสถานะไฟล์และกิ่งปัจจุบัน |
| `git add .` | นำไฟล์ที่แก้ไขทั้งหมดเตรียมไว้ใน Staging Area |
| `git commit -m "ข้อความ"` | บันทึกประวัติจุดเซฟ (Checkpoint) ลงในเครื่อง |
| `git push` | ส่ง Commit จากเครื่องขึ้นไปยัง GitHub |
| `git pull origin main` | ดึงโค้ดล่าสุดจากกิ่ง main บน GitHub มารวมในเครื่อง |
| `git branch` | ดูรายชื่อ Branch ทั้งหมดในเครื่อง |
| `git checkout -b <ชื่อกิ่ง>` | สร้างกิ่งใหม่และสลับไปกิ่งนั้นทันที |
| `git checkout <ชื่อกิ่ง>` | สลับไปยังกิ่งที่มีอยู่แล้ว |
| `git merge <ชื่อกิ่ง>` | รวมโค้ดจากกิ่งที่ระบุเข้ามายังกิ่งปัจจุบัน |
| `git restore <ชื่อไฟล์>` | ยกเลิกการแก้ไขไฟล์ ย้อนกลับไปเวอร์ชันล่าสุด |
| `git log --oneline` | ดูประวัติ Commit แบบย่อบรรทัดเดียว |
